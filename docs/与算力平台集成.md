# new-api 与算力平台集成方案

## 一、需求概述

将 new-api 集成到算力平台，实现单点登录（SSO）：
- **当前 new-api 认证**：基于 Session，登录后写入 Cookie（username, role, id, status, group）
- **算力平台认证**：基于 JWT，Cookie 中存储 `token` 或 `dcloud_token`，两者取其一
- **JWT 内容**：包含 user_id, user_name, account, role_name, tenant_id, vdc_code(dept_code), project_id 等

## 三、JWT Token 结构

### 3.1 Header
```json
{
  "alg": "HS256",
  "typ": "JWT",
  "key": "dcloud_web"
}
```

### 3.2 Payload
```json
{
  "tenant_id": "888888",
  "role_name": "ai-studio,AI算力角色,oneapicommonrole",
  "vdc_code": "02002I02J02N",
  "role_id": "11,1734863057562652673,1912344289895895044",
  "user_id": "1735269794500841474",
  "user_name": "D15012",
  "exp": 1767659823,
  "authorities": [
    "cube-studio",
    "AI算力角色-通用",
    "oneapicommonrole"
  ],
  "client_id": "dcloud_web",
  "account": "D15012"
}
```

### 3.3 字段说明
| 字段 | 说明 | 用途 |
|------|------|------|
| `user_id` | 算力平台用户唯一ID | 作为 external_user_id 关联本地用户 |
| `user_name` / `account` | 用户名 | 映射到 new-api 的 username |
| `tenant_id` | 租户ID | 多租户隔离 |
| `vdc_code` | 部门编码 | 映射到 dept_id |
| `role_name` | 角色名称列表（逗号分隔） | 角色映射来源 |
| `exp` | 过期时间戳 | JWT 有效性验证 |

## 五、角色映射方案

### 5.1 角色对照表

算力平台角色与 new-api 角色映射关系：

| 算力平台角色 | new-api 角色 | role 值 |
|-------------|-------------|---------|
| `oneapiguestrole` | 访客用户 | `0` (RoleGuestUser) |
| `oneapicommonrole` | 普通用户 | `1` (RoleCommonUser) |
| `oneapiadminrole` | 管理员 | `10` (RoleAdminUser) |
| `oneapirootrole` | 超级管理员 | `100` (RoleRootUser) |

### 5.2 角色解析逻辑

算力平台的 `role_name` 字段可能包含多个角色（逗号分隔），例如：
```
"role_name": "ai-studio,AI算力角色,oneapicommonrole"
```

**解析规则**：
1. 将 `role_name` 按逗号分割成角色列表
2. 在角色列表中查找匹配的 new-api 角色标识（`oneapiguestrole`, `oneapicommonrole`, `oneapiadminrole`, `oneapirootrole`）
3. 按照优先级从高到低匹配：`oneapirootrole` > `oneapiadminrole` > `oneapicommonrole` > `oneapiguestrole`
4. 找到第一个匹配的角色后，映射为对应的 new-api role 值
5. 如果未找到任何匹配角色，默认使用 `RoleCommonUser` (1)

### 5.3 角色互斥说明

算力平台的角色设计是互斥的，一个用户在同一时刻只能拥有一个 new-api 相关角色。这样可以确保权限控制的清晰性。

### 7.3 JWT 验证与用户同步逻辑

#### 7.3.1 DCloudAuth 中间件流程

```
1. 检查 DCLOUD_INTEGRATION_ENABLED，如未启用则跳过
2. 从 Cookie 中读取 dcloud_token（或配置的 cookie 名）
3. 如不存在，尝试读取 token 作为备选
4. 使用 DCLOUD_JWT_SECRET 验证 JWT 签名
5. 解析 JWT Payload 获取用户信息
6. 调用 ParseDCloudRole() 解析角色
7. 查询本地用户：
   - 优先通过 external_user_id + tenant_id 查询
   - 如不存在，通过 username 查询
8. 如用户不存在，自动创建新用户
9. 如用户存在，更新用户信息（角色、部门等）
10. 写入 Session（username, role, id, status, group）
11. 继续后续中间件处理
```

#### 7.3.2 角色解析函数

```go
// ParseDCloudRole 从算力平台 role_name 解析 new-api 角色
func ParseDCloudRole(roleName string) int {
	if roleName == "" {
		return RoleCommonUser
	}
	
	roles := strings.Split(roleName, ",")
	roleSet := make(map[string]bool)
	for _, r := range roles {
		roleSet[strings.TrimSpace(r)] = true
	}
	
	// 按优先级查找
	for _, priorityRole := range DCloudRolePriority {
		if roleSet[priorityRole] {
			return DCloudRoleMap[priorityRole]
		}
	}
	
	return RoleCommonUser
}
```

#### 7.3.3 用户同步函数

```go
// SyncDCloudUser 同步算力平台用户到本地
func SyncDCloudUser(jwtData *DCloudJWTClaims) (*User, error) {
	// 1. 尝试通过 external_user_id + tenant_id 查找用户
	user, err := GetUserByTenantAndExternalId(jwtData.TenantId, jwtData.UserId)
	if err != nil && !errors.Is(err, gorm.ErrRecordNotFound) {
		return nil, err
	}
	
	role := ParseDCloudRole(jwtData.RoleName)
	
	if user == nil {
		// 2. 用户不存在，创建新用户
		user = &User{
			Username:       jwtData.UserName,
			DisplayName:    jwtData.UserName,
			Role:           role,
			Status:         UserStatusEnabled,
			TenantId:       jwtData.TenantId,
			DeptId:         jwtData.VdcCode,
			ExternalUserId: jwtData.UserId,
			Group:          "default",
		}
		err = user.Insert(0)
	} else {
		// 3. 用户存在，更新信息
		user.Role = role
		user.TenantId = jwtData.TenantId
		user.DeptId = jwtData.VdcCode
		err = user.Update(false)
	}
	
	return user, err
}
```

## 八、多租户支持

### 8.1 租户隔离策略

算力平台支持多租户架构，new-api 需要实现以下隔离策略：

1. **数据隔离**：通过 `tenant_id` 字段区分不同租户的数据
2. **用户隔离**：同一算力平台用户在不同租户下视为不同用户
3. **Token 隔离**：用户的 API Token 按租户隔离

### 8.2 租户识别流程

```
1. 从 JWT 中解析 tenant_id
2. 将 tenant_id 写入用户表的 tenant_id 字段
3. 将 tenant_id 写入 Session
4. 后续请求通过 Session 中的 tenant_id 进行数据过滤
```

### 8.3 数据查询过滤

所有涉及用户数据的查询都需要增加 `tenant_id` 过滤条件：

```go
// 示例：查询用户列表
func GetUsersByTenant(tenantId string, pageInfo *common.PageInfo) ([]*User, error) {
	var users []*User
	err := DB.Where("tenant_id = ?", tenantId).
		Order("id desc").
		Limit(pageInfo.GetPageSize()).
		Offset(pageInfo.GetStartIdx()).
		Find(&users).Error
	return users, err
}
```

## 九、安全考虑

### 9.1 JWT 安全

1. **签名验证**：必须使用 `DCLOUD_JWT_SECRET` 验证 JWT 签名
2. **过期检查**：验证 `exp` 字段，拒绝过期 Token
3. **算法限制**：仅允许 HS256 算法，防止算法切换攻击

### 9.2 Cookie 安全

1. **HttpOnly**：建议设置 HttpOnly 标志
2. **Secure**：生产环境建议使用 Secure 标志（HTTPS）
3. **SameSite**：根据部署情况设置 SameSite 属性

### 9.3 会话安全

1. **Session 固定攻击防护**：用户登录后重新生成 Session ID
2. **并发登录控制**：可选限制同一用户多处登录

## 十三、技术实现细节

### 13.1 JWT 库选择

本项目使用 `github.com/golang-jwt/jwt/v5` 作为 JWT 解析库（而非已停止维护的 `github.com/dgrijalva/jwt-go`）。

**关键实现**（middleware/dcloud.go）：
```go
import "github.com/golang-jwt/jwt/v5"

// DCloudJWTClaims 实现 jwt.Claims 接口
type DCloudJWTClaims struct {
	TenantId    string   `json:"tenant_id"`
	RoleId      string   `json:"role_id"`
	UserId      string   `json:"user_id"`
	UserName    string   `json:"user_name"`
	VdcCode     string   `json:"vdc_code"`
	RoleName    string   `json:"role_name"`
	Authorities []string `json:"authorities"`
	AccountId   string   `json:"account"`
	jwt.RegisteredClaims
}

// 验证 JWT Token
token, err := jwt.ParseWithClaims(tokenString, &DCloudJWTClaims{}, func(token *jwt.Token) (interface{}, error) {
	return []byte(common.DCloudJWTSecret), nil
})
```

### 13.2 密码加密方式

为了与算力平台保持一致，密码加密使用 MD5 + SHA1 组合方式。

**实现**（common/crypto.go）：
```go
// CryptoPass 使用算力平台相同的密码加密方式 (MD5 + SHA1)
func CryptoPass(raw string) (string, error) {
	return SHA1(Md5Fn(raw))
}

// ValidateCryptoPass 验证密码是否匹配
func ValidateCryptoPass(password string, hash string) bool {
	computedHash, err := CryptoPass(password)
	if err != nil {
		return false
	}
	return computedHash == hash
}
```

**使用场景**：
- 用户注册/登录时的密码加密和验证
- 用户修改密码时的验证

**注意**：双因素认证（2FA）的备用码验证仍使用 bcrypt，因为它是本地存储的安全凭据，与算力平台无关。

## 十五、前端 Session 检查机制

### 15.1 问题描述

DCloud SSO 认证流程中，后端通过 JWT 验证用户身份并写入 Session，但前端无法感知这一过程：
- 后端 Session 已写入（用户已认证）
- 前端 `localStorage.user` 不存在
- 导致 `PrivateRoute` 重定向到登录页

### 15.2 解决方案

在前端 `PrivateRoute` 和 `AdminRoute` 组件中增加 Session 状态检查：

1. 检查 `localStorage.user` 是否存在
2. 如不存在，调用 `/api/user/self` API 检查后端 Session
3. Session 有效则获取用户信息并写入 `localStorage`
4. Session 无效则重定向到登录页

### 15.3 核心代码（web/src/helpers/auth.jsx）

```javascript
// 检查后端 Session 状态（用于 DCloud SSO 等场景）
export async function checkSessionStatus() {
  try {
    const res = await API.get('/api/user/self', { skipErrorHandler: true });
    const { success, data } = res.data;
    if (success && data) {
      setUserData(data);
      return true;
    }
  } catch (error) {
    console.debug('Session check failed:', error?.message);
  }
  return false;
}
```
